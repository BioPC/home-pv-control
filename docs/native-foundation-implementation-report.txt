2. ARCHITECTURE IMPLEMENTED
Native config-entry setup/config flow and six entity platforms; immutable approved model boundaries; entry-owned lifecycle and serialized/coalescing scheduler; read-only legacy capture/preview/import transaction framework; separate configuration, history and execution storage.
The scheduler uses a 5-second startup barrier, 10-second wake and forced full evaluation at least every 30 seconds. Ordinary telemetry only marks dirty state. Full control/HBC evaluation is not implemented.
Reports and inverter/base contain typed boundaries only, not report generation or device execution.

3. STORAGE SCHEMAS
All store envelopes are schema 1 and include kind, revision, payload and payload checksum.
  configuration: PlantConfiguration plus bounded idempotent ImportTransaction records.
  history: separate runtime-history boundaries, accuracy eligibility schema 11 / attribution revision 22.
  execution: ledger schema 1; ownership, uniquely identified physical-operation records, restore obligations, maintenance, HBC override recovery, Night Restore recovery and bounded evidence.
Writes are validated, serialized, fsynced and atomically replaced. Referenced evidence cannot be silently discarded. Unknown execution and unresolved restore obligations survive reload. A missing ledger beside existing configuration blocks startup rather than creating empty recovery.
No universal power-loss guarantee is claimed; Windows cannot validate every POSIX filesystem guarantee.

4. ENTITY IDS CREATED
178 intended native IDs: 16 switches, 50 numbers, 21 selects, 84 configuration texts, 4 sensors and 3 binary sensors.
Full list: HPVC-2.0-foundation-entity-ids.csv.
Priority entities include switch.hpvc_enabled; number.hpvc_inverter_count and the nine thresholds; select.hpvc_selected_inverter; sensor-reference text entities; sensor.hpvc_migration_state; sensor.hpvc_installed_version; binary_sensor.hpvc_physical_writes_authorized; binary_sensor.hpvc_recovery_required; binary_sensor.hpvc_required_inputs_ready.
Enable is intent only. Physical-write authorization and required-input readiness remain Off.
HA may suffix IDs already owned by legacy entities; no registry takeover is performed in this foundation.

5. LEGACY IMPORTER STATUS
Detection, read-only snapshot, strict validation, preview, exact 232-helper mapping and idempotent transaction persistence are implemented. Missing versus zero is preserved, malformed values/JSON are rejected, inactive-slot configuration is retained, and import cannot overwrite a completed native configuration import.
Native master intent starts Off after import. Saved former enable intent is retained only as provenance. Auto-managed identities remain provisional until registry reconciliation.
No HBC/Node-RED files are edited. No legacy disable, flow removal, context bridge, physical reconciliation, ownership handoff or cutover occurs. User-owned external references are explicitly uninspected and not rewritten. Runtime-history journal migration is deferred.

7. NO PHYSICAL WRITE PATH
There is no native dispatcher or concrete writable generic/Hoymiles/Enphase adapter. There is no HBC writer or final control engine.
Coordinator and execution-snapshot authorization properties return literal False; the physical-write binary sensor also returns literal False.
Every ownership enum state was tested, including data records named native_active: no state or user enable intent can change authorization.
A source AST test rejects HA service access/call methods and HTTP/MQTT actuator transports in native source. Runtime service-call traps are exercised across setup, edits, import, evaluation, reload and unload.
Ledger lifecycle transitions are persisted DATA ONLY. No transition executes a service.
Legacy Node-RED can continue its existing operation; this guarantee applies to the new native integration.
